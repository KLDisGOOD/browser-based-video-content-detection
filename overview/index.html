01

Project Overview

The problem. Detect inappropriate visual content in videos without exposing that video to a server. Moderation is usually server-side: upload the video, classify remotely. This prototype refuses that default; all processing happens locally in the browser.

The key constraint. Video processing must happen locally in the browser. No frame data leaves the device for classification. Every other decision (model size, sampling rate, backend, UX) follows from that one rule.

The privacy model. Video frames stay on the user's device. The only network traffic is a one-time fetch of the model and library bundles, which the browser caches. After that, a scanned video never leaves the device. The only output is a boolean and a number, shown locally.

Prototype vs. production. The prototype prioritizes simplicity, portability, and browser compatibility. A production implementation would likely replace several pipeline stages while preserving the overall architecture. As shipped, the prototype fetches the model from a CDN on first load; it is local-inference, not offline-by-default. A production build would bundle model assets and register a Service Worker for offline use.

The output

{
  "contains_inappropriate_content": true,
  "confidence": 0.86
}

Two fields. The boolean is the decision; the number is a confidence estimate derived from temporal aggregation, not a guaranteed probability. Reliable probability calibration would require a labeled validation dataset together with techniques such as Platt scaling or isotonic regression.

Why browser-side ML is hard

  • Limited compute. Mobile chips are far weaker than the desktop hardware most ML tooling assumes.
  • Memory restrictions. Browsers cap per-tab memory well below native app budgets; mobile WebViews are tighter still.
  • Battery constraints. Sustained inference drains battery and triggers thermal throttling, which then slows the scan further.
  • Device variability. GPU drivers, WebGL/WebGPU support, WASM SIMD, and codec support vary across the long tail of devices.

Architecture Overview

A linear pipeline of discrete stages. Each stage has one job, a known cost, and a defined handoff. The pipeline is stateless between runs: nothing from one scan leaks into the next.

FIG. 1

End-to-end pipeline. A muted <video> feeds sampled frames to a canvas rasterizer; TensorFlow.js runs MobileNetV2Mid with automatic backend fallback. Per-frame probabilities become a confidence estimate, a policy layer emits the JSON verdict, and the UI applies the matching restriction behavior.

The pipeline, as code

// frame extraction → inference → confidence → policy → UI

video   = HTMLVideoElement(muted, paused)     // prototype decoder surface
frames  = sample(video, fps=2, cap=maxFrames) // uniform, bounded (prototype)
tensors = frames.map(downscaleTo(224))        // canvas drawImage
scores  = tensors.map(classify)               // MobileNetV2Mid, 5 classes
verdict = estimateConfidence(scores)          // persistence + peak
json    = policy.decide(verdict)              // { contains, confidence }
ui.apply(policy.tier(confidence))             // banner / blur / restrict

Separation of concerns

Detection and policy are intentionally separated so thresholds and user experience can evolve independently of the underlying ML model:

Inference            // model + frame extraction (swap the model without touching policy)
   ↓
Confidence Estimation // temporal aggregation (tune without touching the model or UI)
   ↓
Policy Layer          // confidence → tier mapping (change thresholds, add tiers, add review)
   ↓
User Interface        // tier → restriction behavior (change UX without touching inference)

The model can be replaced, thresholds re-tuned, or a new tier inserted (for example, a "review" tier routing to a human moderator) without touching the other layers.

Stage responsibilities

  • Video Input. File upload avoids CORS (same-origin blob:); URL input depends on the host's CORS headers, so it is best-effort.
  • HTML Video Element. A muted, paused <video> is the only portable decoder. Seeking to fixed timestamps gives reproducible samples and skips decoding every frame. This is a prototype choice; production would move to WebCodecs frame extraction.
  • Frame Sampling. Representative frames, not every frame. 2 fps with a cap keeps cost predictable (prototype choice; production would use adaptive temporal refinement).
  • Canvas Downscaling. A 1280×720 frame (~921k px) becomes 224×224 (~50k px), cutting tensor size ~18× at negligible cost.
  • TensorFlow.js Runtime. Hardware-accelerated inference with automatic backend selection (see §5).
  • Classifier. Returns all five class probabilities per frame, not top-1, so borderline frames are not rounded away.
  • Confidence Estimation. Combines many frames so the decision does not hinge on a single noisy one.
  • Policy Layer & UI. Map confidence to a restriction tier and render it.
03

Model Selection

The prototype uses NSFW.js MobileNetV2Mid, a MobileNet-v2 classifier on TensorFlow.js with five classes: Drawings, Hentai, Neutral, Porn, Sexy. It was chosen because it is TensorFlow.js-compatible, runs in the browser with no native bridge or server round-trip, is lightweight (a few MB, cacheable), has reasonable latency (tens of milliseconds per frame with a GPU backend), and uses depthwise separable convolutions designed for mobile.

This model was selected as a practical prototype choice, not as the final production model. Its taxonomy is generic; a production system would evaluate against the product's own content policy and labeled data.

Future production candidates

// candidates to evaluate for a production build
- MobileNetV3 (quantized)        // int8, smaller + cheaper, modest accuracy cost
- EfficientNet-Lite              // mobile, good accuracy-per-MAC
- product-specific moderation model // classes match the product's policy

Production model selection would compare these candidates using precision, recall, F1, latency, memory usage, and energy consumption rather than accuracy alone. The decision would depend on accuracy requirements, hardware targets, false-positive tolerance, and dataset quality.

04

Detection Pipeline

Temporal sampling

Uniform sampling: 2 frames per second of video time, with a maximum frame cap. A 30-second clip yields ~60 samples; a 10-minute clip is sub-sampled so total inference stays bounded.

// sampling config (prototype)
fps        = 2          // frames per second of video time
maxFrames  = 120        // hard cap; long videos are sub-sampled
schedule   = uniform    // evenly spaced currentTime seeks

Advantages. Predictable inference budget; lower battery use; works across devices (the cap protects low-end hardware).

Limitations. Short events between samples may be missed. A sub-second flash that starts and ends between two uniform samples is invisible. This is a fundamental limit of any sampled approach, addressed in production by adaptive temporal refinement (§8), not by the frame extractor alone.

Frame processing

Each sampled frame is drawn to a canvas with the longest edge at 224 px, then read as a tensor. Lower resolution means a smaller tensor and fewer spatial positions in the first conv layer; both cut inference cost. Intermediate tensors are released immediately after inference to prevent unnecessary memory growth during long-running scans.

Confidence estimation

Frames are considered together, not one at a time. For each frame we keep the full class probability vector and derive an inappropriate score. Across the whole video, two signals are combined:

// two signals, one confidence estimate
persistence = fraction of frames flagged at per-frame threshold  // sustained-but-mild
peak        = max inappropriate score across all frames            // short explicit flashes

contains    = (persistence >= flagFraction) OR (peak >= flagPeak)
confidence  = blend(persistence, peak)                             // reported in JSON

Persistence catches sustained-but-milder content; peak catches short, high-confidence events. The reported confidence is a calibrated confidence estimate derived from temporal aggregation. Reliable probability calibration would require a labeled validation dataset together with techniques such as Platt scaling or isotonic regression; the shipped thresholds are reasonable hand-picks pending data-driven tuning.

Streaming pipeline

The pipeline processes one frame at a time rather than buffering an entire video in memory. Each decoded frame is immediately classified, aggregated into running statistics, and released. Only lightweight aggregate state is retained: peak confidence, persistence statistics, counters, and timestamps. Memory usage therefore scales approximately with frame size rather than video duration, making the approach suitable for long videos and memory-constrained mobile devices.

05

Browser & Mobile Performance

Browser ML lives inside a hard mobile envelope. The prototype stays inside it by budgeting the inference budget and yielding between frames.

  • Mobile GPUs vary a lot. A flagship can be 5 to 10× faster than a low-end Android part.
  • Browser memory is limited. Per-tab budgets are far below native app budgets; mobile WebViews are tighter still.
  • Continuous inference hits battery. Sustained GPU/WASM work drains battery and triggers thermal throttling, which then slows the scan mid-run.

Backend selection

Backends are probed in fallback order; the first one that initializes is used.

// fallback order
await tf.setBackend('webgpu')   // fastest, where supported
   ?? await tf.setBackend('webgl')   // broad GPU default
   ?? await tf.setBackend('wasm')    // CPU + SIMD
   ?? await tf.setBackend('cpu')     // universal, slowest
BackendRoleNotes
WebGPUHighest performance when supportedModern browsers; not yet universal on mobile
WebGLBroad GPU accelerationThe realistic default on most mobile browsers today
WASMCPU-based optimized executionUsed when neither GPU path is available; benefits from SIMD
CPUUniversal fallbackAlways available; slowest; guarantees the pipeline runs somewhere

Keeping the page responsive

The implementation performs asynchronous frame processing and deliberately yields to the browser event loop between inference operations. This prevents rendering, scrolling, input handling, and progress updates from being blocked during long scans. A hard cap on frames bounds total work regardless of video length, and the model loads lazily when the user triggers a scan, not on page load.

Content Restriction UX Proposal

The prototype's default (blur plus confirmation) is one point on a spectrum. Production behavior should depend on the confidence level. Three scenarios follow, each with UI behavior, reasoning, and tradeoffs. The mockups reuse the prototype's own visual language, and demonstrate that inference and UI policy are decoupled: the policy layer maps a confidence value to a tier, and the UI renders that tier.

Low · 0.50–0.70
Potentially inappropriate content detected.

Warning banner above the video; playback continues. The video element stays mounted and untouched.

Medium · 0.70–0.90 · prototype
Potentially inappropriate content detected. Tap to continue viewing. Acknowledge

Playback paused; CSS blur overlay applied; explicit interaction required to reveal. This is the prototype's default behavior.

High · >0.90
⌀
This video has been restricted because inappropriate content was detected.
Request review

Video area replaced by a restriction panel. Underlying content is unmounted, not merely obscured.

Low Confidence 0.50–0.70

UI: warning banner above the video; playback allowed. Message: "Potentially inappropriate content detected."

Why: reduces unnecessary interruptions. At this confidence a hard block would be wrong more often than right, so it suits apps that prioritize fewer false positives.

Advantages
  • Minimal disruption to viewing.
  • Good UX for low-stakes contexts.
Disadvantages
  • Content may still be visible; the warning signals but does not prevent exposure.

Suitable for: lower-risk environments where user agency beats hard protection.

Medium Confidence 0.70–0.90

This is the prototype implementation.

UI: pause playback; apply a CSS blur overlay; show "Potentially inappropriate content detected. Tap to continue viewing."; require explicit interaction to reveal and resume.

Why: the blur means a user scrolling past or autoplaying a flagged video never sees the content without an affirmative action. False positives stay reversible, and the <video> stays mounted, so nothing reflows.

Advantages
  • Simple: one CSS filter on an existing element.
  • Low overhead: blur is GPU-composited, near-free.
  • Smooth interaction: unblur is one transition on the same element.
Disadvantages
  • Content remains under the blur; coarse structure is still perceptible.
  • Not suitable for strict moderation that requires content to be unavailable, not obscured.

Suitable for: general platforms that want protection without over-blocking, where false positives are common enough that a reversible interaction beats a hard wall.

High Confidence >0.90

UI: pause playback; replace the video area with a restriction panel; show "This video has been restricted because inappropriate content was detected." The underlying video element is unmounted or hidden, so its content is not in the DOM.

Why: at this confidence the system's best estimate is that the content is genuinely inappropriate; the right action is to make it unavailable, not blurred.

Advantages
  • Strongest protection: content is removed, not obscured.
  • Prevents accidental viewing in any context, including autoplay and scroll-past.
Disadvantages
  • False positives hit harder; a wrongly restricted video is fully unavailable until reviewed.
  • Requires appeal/review flows, or the system is unusable when the model is wrong.

Suitable for: child safety and strict content platforms where letting bad content through costs more than wrongly blocking it.

Policy is decoupled from detection. The aggregation layer emits a confidence value; the mapping from confidence ranges to UI behaviors is a policy table. Changing thresholds or adding a tier does not require touching the detection pipeline.

Performance Tradeoffs & Alternatives

Sampling frequency

DirectionEffect
Higher sampling +Better temporal coverage; shorter events become detectable.
Higher sampling −More CPU/GPU use and battery drain; linear in frame count.
Lower sampling +Faster scans, more efficient inference budget use.
Lower sampling −Greater chance of missing events between samples.

Model size

DirectionEffect
Large models +Better accuracy on benchmarks.
Large models −Higher per-frame latency, larger downloads, more memory.
Small models +Faster inference, smaller payload, lower RAM.
Small models −Lower accuracy; more borderline frames misclassified.

Alternative approaches

Server-side inference

  • + Larger models available; scaling handled by backend; thresholds tuned centrally.
  • − Violates the local-processing requirement; privacy concerns (video leaves the device); needs backend infrastructure with its cost, latency, and failure modes.

Vision Transformers

  • + Strong image understanding; often beat CNNs on classification benchmarks.
  • − Usually too expensive for browser/mobile inference; parameter counts and attention compute are an order of magnitude beyond what a phone GPU sustains at interactive rates.

WebCodecs

  • + Efficient sequential frame extraction with lower decode overhead, replacing repeated seeking through the video.
  • − More implementation complexity; browser compatibility considerations, especially on the mobile WebView long tail. WebCodecs provides frame extraction and lower decode overhead; it does not by itself fix temporal sampling. Improved recall comes from combining WebCodecs with adaptive temporal refinement.
08

Production Improvements

The prototype uses uniform sampling because it is the simplest correct baseline. The biggest efficiency win available to a production build is to stop spending the inference budget on visually identical frames. The adaptive refinement pipeline below is the production design the prototype's uniform scan stands in for.

Adaptive temporal refinement

Scene change detection

Detect major visual transitions between consecutive frames by comparing cheap downsampled thumbnails (luma difference), not by running the model. Purpose: avoid wasting inference on visually identical frames.

Midpoint activity probes

Midpoint activity probes decode one or more additional frames between coarse samples and perform inexpensive thumbnail or luma comparisons before deciding whether full model inference is warranted. Additional model inference only occurs if activity is detected.

Adaptive refinement

Coarse-then-refine, instead of uniformly dense:

// coarse → suspicious → refine → decide
1. coarse scan        low fps across the whole video          // as in the prototype
2. suspicious region  increase density only where probes     // spend the inference budget where it matters
                      flag scene change or activity
3. final decision     higher confidence, limited extra       // raises peak without re-running
                      inference                                // the whole scan

Regions of Interest (ROIs)

Regions identified during the coarse scan with elevated confidence become Regions of Interest (ROIs). Under a fixed inference budget, these regions receive additional temporal sampling before low-risk regions.

The shape of the win. Adaptive refinement does not improve the classifier itself. It improves how the available inference budget is allocated by increasing sampling density only in regions that appear suspicious during the coarse scan.

Limitations

  • CORS for remote URLs. The URL workflow exists to satisfy the assessment requirements. In practice, many remote video hosts prevent browser frame extraction through CORS restrictions or hotlink protection. For browser-only inference, local file upload is the most reliable workflow.
  • Some hosts cannot expose frames to canvas. Even when a URL loads, hosts serving media in ways incompatible with cross-origin canvas access cannot be scanned. URL is best-effort; file is reliable.
  • Uniform sampling can miss short events. A sub-second event between two samples is invisible. This is a fundamental sampled-approach limit, addressed in production by adaptive temporal refinement combined with WebCodecs frame extraction.
  • False positives and false negatives are expected. The model is a probabilistic classifier, not an oracle. Beach, medical, and skin-heavy-but-neutral frames can trigger; stylized or drawn content can evade. Thresholds bias one direction but cannot eliminate errors.
  • The prototype model is not trained for a specific taxonomy. NSFW.js's five classes are generic; a product with a specific policy needs a model whose classes match it.
  • Confidence calibration needs labeled data. Shipped thresholds are hand-picks. Reliable probability calibration would require a labeled validation set together with techniques such as Platt scaling or isotonic regression.
  • Hardware performance varies. The same scan can take seconds on a flagship and tens of seconds on a low-end phone, which is why the §5 table is a template, not a single number.

Production Roadmap

Short-term

  • Benchmark across devices. Fill the §5 table across a device matrix (flagship, mid-range, low-end Android, iOS Safari) and pin the backend per device class instead of auto-fallback.
  • Larger evaluation dataset. A labeled corpus spanning the product's real categories, including edge cases (beach, medical, art, animation).
  • Confidence calibration. Sweep per-frame and video-level thresholds against the labeled set; report precision, recall, F1, latency, memory, and energy; pick by the chosen operating point.

Medium-term

  • WebWorker inference. Move the model and inference loop off the main thread so the UI never competes with classification.
  • WebCodecs frame extraction. Replace HTMLVideoElement seeking with VideoDecoder for efficient sequential frame extraction and lower decoding overhead, enabling denser or adaptive temporal analysis without repeatedly seeking.
  • Adaptive temporal refinement. Ship the coarse-then-refine pipeline from §8, with midpoint probes and Regions of Interest.
  • Quantized production model. int8 MobileNetV3 or EfficientNet-Lite via the WASM(SIMD) backend for devices without strong GPUs.

Long-term

  • Product-specific moderation model. Trained on the product's policy and taxonomy, replacing the generic NSFW.js classes.
  • Device-specific optimization. Pin backend, input resolution, and sampling density per device class so a low-end phone gets a smaller model and a coarser scan instead of stalling.
  • Continuous benchmarking and tuning. Re-run the device matrix as browsers, drivers, and models evolve; thresholds drift over time.

What this roadmap is not. Not a claim that the prototype becomes production-ready by checking items off. Each item is a project with its own validation cost; several (WebCodecs, custom training, device benchmarking) are substantial.
